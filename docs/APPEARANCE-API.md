# Appearance API

Import from `src/appearance/index.ts`: `DARK_ACCENTS`, `LIGHT_ACCENTS`, `MODE_COLORS`, `accentPalette`, `contrastRatio`, `applyAccent`, `loadAppearance`, `saveAppearance`, `resolveMode`, `APPEARANCE_KEY`, `EXISTING_THEME_KEY`; types `AppearanceMode`, `AccentPalette`, `ModePreference`, `Appearance`, `AppearanceStorage`, `AccentRoot`.

`applyAccent(root, mode, accentId): AccentPalette` writes `--accent`, `--accent-hover`, `--accent-active`, `--accent-soft`, `--accent-contrast` and `data-accent`/`data-mode`. Unknown ids use purple for that mode. It deliberately leaves `data-theme` alone: the existing theme controller owns dark/light/system. The root needs only style.setProperty and dataset; no DOM globals or UI imports are required.

`loadAppearance(storageGetter?): {dark,light}` reads `aive.appearance.accents`. `saveAppearance(choices, storageGetter?): boolean` returns false for blocked/full storage; keep the current choices in UI session memory if persistence fails. Changes are not project edits and create no undo entries. Save both choices using `{...current, [mode]: chosenId}`. Unknown/corrupt data defaults independently. `resolveMode(preference?, {storage?,systemLight?}?)` reads the existing `aive.theme` key (default dark), with the existing `(prefers-color-scheme: light)` system behavior. Pass the current explicit preference when storage is blocked.

## UI wiring (no UI/CSS changed)

Call `applyAccent(document.documentElement, mode, choices[mode])` after `initTheme` at startup. Repeat from the existing `onThemeChange` callback on toggle/system changes, and when the accent selector changes; derive mode with `resolveMode` or the existing resolved `currentTheme`. Load once, retain choices in session, save on explicit selection. For first paint the UI agent should add the same initialization at the existing pre-paint bootstrap boundary in index.html. No storage listener or UI subscription is created by this module.

First entries copy existing tokens from `src/ui/tokens.css`: dark #7c5cff / #8f74ff / #6a49f0 / rgba(124,92,255,.16); light #6c47ff / #5b37f0 / #4f2ce0 / rgba(108,71,255,.1). Names and ids can become translation keys in the UI.

The requested `accentContrast >= 4.5` rule requires **black text on the unchanged dark raw accent**: existing white on #7c5cff does not pass. Existing actual buttons use the darker `--accent-fill` and white text, so keep those legacy default fill tokens to retain their current appearance. The new --accent-contrast variable does not alter those existing buttons until wired. A complete migration to raw --accent as the button fill would change their look; do not claim otherwise. Hover/active text contrast is not asserted by the requested base-accent test.

Existing aliases needing deliberate UI-agent wiring: --accent-pressed → --accent-active; --text-on-accent → --accent-contrast only for components whose fill is --accent. --accent-fill, --accent-fill-hover, --accent-text, --accent-border, --focus-ring and --region-accent remain separate legacy tokens. They must be made palette-aware to recolour the whole editor; do not blindly alias their distinct AA text/fill roles. This module sets exactly the five requested variables, so existing CSS alone will not yet recolour every purple surface.

`contrastRatio(foreground, background, panel?)` implements WCAG sRGB contrast with rgba compositing over panel; exported mode panel/text values match current tokens. The eight palettes per mode are immutable.
