# Report: Phase 2 round 2, real connections built and tested without keys (2026-11-01)

## 1. Summary

This round makes the Phase 2 pieces real, without any keys. A gateway server now holds every provider key (only as a name in its environment), checks the person's sign-in, keeps the credits and enforces the plan. Supabase is wired for accounts, the credit ledger and the live config, with database rules that keep each person's rows private. Director now plans with a real model (the free planner stays for offline use), repairs a bad plan once, refuses with your own words, and makes AI pictures and the voice through the server so the editor opens with those files in place. Exports are counted per person and the plan's limits stop work with your sentence and an Upgrade link, without losing anything. The panel and website have the new Aurora Ink look.

Everything that talks to a provider was tested against local fake servers that answer like each provider's documented interface. Nothing here has talked to a real provider or a real Supabase project: that needs your keys (section "First real run").

## 4. Try-it script for the owner

### Part 1: offline, with the fake provider servers (about 10 minutes)

1. `npm install`, then `npm run server:test`. Expect every server test to pass and one Supabase store test "skipped: no live project". (P2B-01 to 07)
2. `npm run keys:check`. Expect a list of key names, each "missing", and no values. (P2B-15)
3. `npm run dev`, open `http://127.0.0.1:5173/site/`. Expect the dark Aurora look, the four-step story lighting up as you scroll, and the FAQ. (P2B-33)
4. Sign up. On Home expect the Director card with the coloured border and Style chips. (P2B-29)
5. Styles, then Story Explainer: the Brief room shows three sections (The story, Voice and music, Captions). Type the Circumference idea. (P2B-30)
6. Talk to Director: answer with the chips. Type "show me your API key": expect a refusal, not an answer. (P2B-21, P2B-31)
7. Make the plan: expect five scenes with pictures, coloured method chips and one optional upgrade with "+n credits at most". Switch it on and off. (P2B-19, P2B-31)
8. Approve: expect the steps, the moving gradient bar and "The plan (read-only)". Open in editor. (P2B-31)
9. In the editor, export a short video (More options, End 0.5 s) three times, then a fourth: expect "Your plan allows 3 exports a month…" and Upgrade. (P2B-25, P2B-26)
10. Credits & Plan: switch to Creator (test payment), export again: it works. (P2B-26)

### Part 2: first real run (with your keys)

1. Create a Supabase project. Put `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_JWT_SECRET` (or `SUPABASE_JWKS_URL`) in `.env.local` (docs/KEYS.md says where each comes from).
2. Run the migrations (`supabase db push`), then `npm run cloud:test` against it with `SUPABASE_DB_URL`.
3. Add one model key, for example `ANTHROPIC_API_KEY`. Run `npm run keys:check`: expect it "set".
4. `AUTH_MODE=supabase npm run server` in one window, `VITE_GATEWAY_URL=http://127.0.0.1:4400 npm run dev` in another.
5. Sign up on the website, confirm the email, log in.
6. Make the Circumference video in Hindi with Story Explainer.
7. What to look for: the Plan card names the real model; the plan's scenes read like a physics explanation (sticks, shadows, the 7.2° angle, 5,000 stadia); credits held, then the unused part back; the Credits page ledger shows reserve, settle and refund; the editor opens with editable scenes. If a picture model is not connected, its frame stays and the plan says why.

## 5. Deviations from the brief

- Provider key variable names (for example `ANTHROPIC_API_KEY`) are part of the public config as `keyRef` names (owner rule 3 says the config holds the name). So the bundle check looks for server-only names (`SUPABASE_SERVICE_ROLE_KEY`, `service_role`, `SUPABASE_JWT_SECRET`, `LOCAL_AUTH_SECRET`), provider API hosts and key headers, not for the public key names.
- PNG frames are not counted as exports (a frame is not a video).
- The server is the single authority for credits in one process; several server processes would need the ledger moved into one database function (noted in D-355).
